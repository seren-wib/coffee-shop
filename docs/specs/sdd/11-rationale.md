## 11. 설계 근거

기술 결정이다. 바뀌면 옛 항목은 두고 새 항목을 단다. 요구사항 수준 정책은 SRS 7절에 있다.

### 11.1 확정

- 2026-11-17: Cloudflare 프록시를 켜고 SSL/TLS 모드는 Full (strict)로 한다. 원 서버(EC2)에는 Cloudflare Origin CA 인증서를 둔다. HTTP → HTTPS 전환은 Cloudflare의 Always Use HTTPS로 한다(NFR-4, NFR-5). 버린 것: DNS only + 서버에서 Let's Encrypt(인증서 갱신 작업이 생기고 EC2 주소가 DNS로 그대로 드러남), Flexible 모드(Cloudflare와 EC2 사이가 평문). 이유: 유지보수성(인증서 갱신 없음), 보안(공개 레포라 원 서버 주소를 숨기는 편이 낫다). (커피샵 Lead 결정, 팀장 위임)
- 2026-11-17: 운영 환경은 서울 리전(ap-northeast-2)의 EC2 t3.micro 한 대, Ubuntu 24.04 LTS, Elastic IP 하나다. 인스턴스 안에서 nginx가 프론트엔드 빌드 결과(정적 파일)를 `/`로, `/api/`는 gunicorn(Django)으로 넘긴다. 버린 것: 프론트엔드를 S3·CloudFront로 따로 배포(서비스가 둘로 늘고 도메인 라우팅이 복잡해짐), Vite 개발 서버 그대로 운영(개발용이라 운영에 맞지 않음), Elastic IP 없이 자동 공인 IP(인스턴스를 멈췄다 켜면 주소가 바뀌어 DNS를 다시 고쳐야 함). 이유: 종속성(서비스 하나), 유지보수성(SIP 절차가 짧음). 비용은 SPMP 4절. (커피샵 Lead 결정, 팀장 위임)
- 2026-11-17: 운영 DB는 SQLite를 그대로 쓴다. WAL 모드를 켜고, 하루 한 번 `sqlite3 .backup`으로 백업 파일을 만들어 7개를 남긴다(NFR-25). 버린 것: RDS(비용과 설정이 늘고, 시연 규모에선 동시 쓰기 부하가 작음). 이유: 비용, 종속성. NFR-15 동시 주문 테스트에서 잠금 오류가 나면 다시 정한다. (커피샵 Lead 결정, 팀장 위임)
- 2026-11-17: `users.User`를 Django 커스텀 사용자 모델(`AbstractBaseUser` + `PermissionsMixin`, `AUTH_USER_MODEL = "users.User"`)로 바꾸고 이메일을 로그인 ID로 쓴다. 비밀번호 열은 Django 규칙대로 `password`가 된다(SRS NFR-6 측정 열 이름도 같이 고친다). 버린 것: 지금 모델을 두고 로그인 처리를 직접 작성(토큰 발급, 해시 확인, 권한 확인을 따로 만들어야 하고 simplejwt와 어긋남). 이유: 유지보수성, 테스트 용이성. 아직 마이그레이션이 없어서 지금 바꾸는 비용이 가장 작다. (커피샵 Lead 결정, 팀장 위임)
- 2026-11-17: 운영 환경에서는 Django 관리 사이트(`/admin/`)를 URL에서 빼고, 개발 환경에서만 연다. 관리자 업무는 FR-36 ~ FR-51, FR-56, FR-57 화면으로, 관리자 계정은 관리 명령(FR-53)으로 만든다. 버린 것: 운영에서도 `/admin/` 공개(공격 대상 경로가 하나 늘고, 화면과 별도로 권한을 두 번 관리해야 함). 이유: 보안, 테스트 용이성. (커피샵 Lead 결정, 팀장 위임)
- 2026-11-17: 테이블 정의의 원본은 `backend/*/models.py`와 Django 마이그레이션이다. `backend/schema.sql`은 지우고, 필요하면 `sqlmigrate`로 뽑아 본다. 부분 유니크 인덱스(기본 배송지 하나, 성공 결제 하나)와 CHECK 제약은 모델 `Meta.constraints`로 둔다. 버린 것: `schema.sql`을 원본으로 두기(ORM과 이중 관리, 이미 두 곳이 서로 다름). 이유: 유지보수성, 배포 때 `migrate` 한 번으로 끝남. (커피샵 Lead 결정, 팀장 위임)
- 2026-11-17: `TIME_ZONE = "Asia/Seoul"`, `USE_TZ = True`로 하고, 주문번호 날짜(DR-11)는 `timezone.localdate()`로 정한다. 버린 것: UTC 유지(자정 전후 주문의 날짜가 한국 날짜와 하루 어긋남). 이유: DR-11. (커피샵 Lead 결정, 팀장 위임)

### 11.2 미결

2026-11-17 SDD 작성 중에 생긴 항목이다. 앞의 아홉 개는 설계 본문에 제안대로 적어 두었고, SDD PR 리뷰에서 팀이 받아들이면 11.1절 확정으로 옮긴다. 다르게 정하면 본문을 같은 PR에서 고친다.

- 옵션 용량 저장값을 `200G`, `500G`, `1KG` 코드로 한다(5.0.2절). HW2 초안은 `'200g'` 문자열이었다. 제안 이유: 다른 열거형과 같은 대문자 코드 규칙, CHECK 제약 값이 표시 문자열과 섞이지 않음. 지금 안 정한 이유: 팀 확인 전. 다시 정하는 신호: SDD PR 리뷰.
- 주문 시각 열 이름을 `ordered_at`에서 `created_at`으로 바꾼다(5.6절). 제안 이유: SRS FR-30, FR-44 검증 열이 `created_at` 정렬이고 다른 테이블과 이름이 같아짐. 버릴 안: API에서만 `created_at`으로 바꿔 부르기(모델과 API 이름이 갈라짐). 다시 정하는 신호: SDD PR 리뷰.
- 택배사를 자유 문자열 `courier_name` 대신 코드 `courier_code`로 저장하고 API는 한국어 이름 `courier_name`과 `tracking_url`을 내보낸다(5.6절, 5.10절). 제안 이유: SRS 7.1 고정 목록과 조회 링크 생성. 다시 정하는 신호: SDD PR 리뷰.
- 결제 기록에 시도별 PG 주문 번호 `pg_order_id`(`<주문번호>-P<n>`)를 두고, `payment_method`를 NULL 허용으로, `payments.order_id`를 CASCADE 대신 PROTECT로 한다(4.6.1절, 5.8절). 제안 이유: 토스페이먼츠는 결제 요청마다 `orderId`가 달라야 하고, 재결제(DR-24)가 같은 주문에서 여러 번 일어남. 지금 안 정한 이유: 토스의 `orderId` 재사용 규칙을 스파이크로 확인 전(3.2절). 다시 정하는 신호: 3.2절 스파이크 결과.
- 관리자 취소 승인은 PG 취소를 먼저 하고 DB를 나중에 바꾼다(4.8.7절). HW2 초안 ALG-03은 DB 먼저였다. 제안 이유: PG 오류 때 주문이 `CANCEL_REQUESTED`로 남아 다시 시도할 수 있음. 남는 위험: 두 관리자가 동시에 승인·반려하면 "결제 취소, 주문 결제 완료"가 생길 수 있음(관리자 한 명이라 받아들임). 다시 정하는 신호: 3.2절 스파이크 3단계에서 "이미 취소" 오류 코드를 구별할 수 없을 때, 또는 관리자 계정이 둘 이상이 될 때.
- 토큰을 `localStorage`에 두고 리프레시 토큰 폐기 목록(blacklist)과 돌려쓰기(rotation)를 쓰지 않는다(4.1.3절, 4.1.5절). 버릴 안: httpOnly 쿠키(CSRF 대책과 쿠키 설정이 새로 필요하고, SRS FR-54가 "브라우저 저장소의 토큰 삭제"를 검증함), simplejwt blacklist 앱(로그아웃마다 DB 쓰기, 테이블 두 개 추가). 이유: 종속성, 테스트 용이성. XSS 대책은 CSP(8.6절). 다시 정하는 신호: SDD PR 리뷰, 또는 보안 점검에서 토큰 저장 위치가 지적될 때.
- 관리자 재고 조정은 증감량이 아니라 새 재고 수량을 보낸다(4.7.8절). 남는 위험: 관리자가 화면을 보는 사이 주문으로 줄어든 재고를 덮어씀. 버릴 안: 증감량(`delta`) 전송(화면이 "+10" 입력을 따로 받아야 함). 다시 정하는 신호: SDD PR 리뷰, 또는 시연 데이터로 재고가 어긋난 사례가 나올 때.
- 원두 목록의 원산지 선택지는 프론트엔드 고정 목록으로 둔다(4.3.7절). 버릴 안: 원산지 목록 API(경로 하나 추가, SRS 6.2에 없음). 남는 한계: 목록에 없는 원산지로 등록한 원두는 원산지 필터로 찾을 수 없음. 다시 정하는 신호: 관리자가 새 원산지 원두를 등록할 때.
- EC2 보안 그룹은 443을 Cloudflare 주소 대역에만, 22를 운영자 주소에만 연다(8.3절). 제안 이유: Full strict와 함께 원 서버로 바로 오는 요청을 막음. 남는 일: Cloudflare 주소 대역이 바뀌면 보안 그룹도 바꿔야 함(SMP 1절). 다시 정하는 신호: SIP 3절 작성 때.
- SRS 6.2에 경로 두 개를 더할지: `POST /api/payments/fail/`(결제창 실패 기록, FR-28), `GET /api/admin/products/{id}/`(관리자 수정 화면, FR-38 ~ FR-41)(7.7절). 지금 안 정한 이유: SRS는 머지된 문서라 SRS PR로 따로 고쳐야 함. 다시 정하는 신호: SDD PR 리뷰에서 받아들이면 SRS 6.2를 같은 날 고친다.
- 배포 자동화: 지금 설계는 운영자가 서버에서 `deploy/deploy.sh`를 실행하는 수동 배포다(10.4절). 버릴지 정할 안: GitHub Actions에서 빌드하고 SSH로 올리기(Actions 시크릿에 SSH 키를 두고, 보안 그룹 22번을 GitHub 주소 대역에 열어야 함). 지금 안 정한 이유: CI(STP 7절)가 아직 없음. 다시 정하는 신호: STP 7절 CI가 들어올 때.
- 외부 감시 도구(NFR-23): 5분 간격 HTTP 확인을 무엇으로 할지. 지금 안 정한 이유: 도메인이 정해지지 않음(SRS 7.2). 다시 정하는 신호: 도메인 결정 뒤, 평가 기간(2026-11-22) 전.
- 백업을 인스턴스 밖으로 복사할지(10.5절). 지금은 같은 EBS 볼륨에 7개만 둔다. 지금 안 정한 이유: S3나 EBS 스냅샷은 비용과 권한 설정이 늘어남(SPMP 4절 비용 미작성). 다시 정하는 신호: SPMP 4절 비용 작성 때.
