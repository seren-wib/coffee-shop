## 3. 스파이크

SPMP 5.2절 위험 표의 첫 두 행(SQLite 동시 주문, 토스페이먼츠 응답)을 구현 전에 확인하는 기술 질문이 아래 두 가지다. 2026-11-19에 3.1과 3.2를 돌렸다. 3.2는 7단계 중 6단계(10분 만료)를 빼고 쟀다. 코드는 `spikes/<이름>/`에 커밋하고, README 첫 줄에 질문과 답을 적는다. 결과가 나오면 이 절과 11절을 같은 PR에서 고친다.

### 3.1 sqlite-concurrent-order

- 질문: SQLite(WAL)와 gunicorn 워커 3개에서, 재고 1개 옵션에 동시 주문 10건이 들어오면 성공 1건, 재고 0, 나머지는 잠금 오류 없이 409로 끝나는가(NFR-15)?
- 결론: **그렇다(IMMEDIATE).** 30라운드 모두 201 1건, 409 9건, 500 0건, 재고 0, 주문 1행이었다. 기본값 DEFERRED에서는 30라운드 중 29라운드에서 `database is locked` 500이 나왔다(300건 중 68건). 두 모드 모두 재고가 틀린 라운드는 0이었다.
- 방법: Django 6.1, Python 3.12(실제로 돌린 건 3.14.4, 아래), `DATABASES["default"]["OPTIONS"]`에 `transaction_mode="IMMEDIATE"`, `timeout=20`, `init_command`로 WAL 설정. 4.5.3절의 `create_order`를 그대로 쓰고, gunicorn 워커 3개 앞에서 스레드 10개가 동시에 `POST /api/orders/`를 보낸다. 같은 실험을 `transaction_mode` 기본값(DEFERRED)으로도 돌려 비교한다. 조건마다 10건을 30라운드 돌렸고, 라운드마다 데이터를 다시 넣었다. 코드와 원자료는 `spikes/sqlite-concurrent-order/`.
- 실행 환경: WSL2 Ubuntu 26.04.1(논리 CPU 16개), Python 3.14.4, Django 6.1.1, gunicorn 27.0.1(sync 워커 3개), SQLite 라이브러리 3.46.1, DB 파일은 WSL ext4 디스크. 클라이언트도 같은 PC다. 운영과 같은 EC2 t3.micro(2 vCPU)에서는 재지 않았으므로 응답 시간은 로컬 값이다.
- 결과:

| 단계 | 확인 | 결과 |
| --- | --- | --- |
| 1 | IMMEDIATE, 동시 10건: 201 개수, 409 개수, 500 개수 | 첫 라운드 201 1, 409 9, 500 0. 30라운드 합계 201 30, 409 270, 500 0 |
| 2 | 1 뒤 옵션 재고, 주문 행 수 | 재고 0, 주문 1행(주문 항목 1행, 장바구니 9행 남음). 30라운드 모두 같음 |
| 3 | DEFERRED, 동시 10건: `database is locked` 발생 횟수 | 첫 라운드 0. 30라운드 합계 300건 중 68건(29라운드에서 1~4건씩). 재고·주문 행은 30라운드 모두 맞음 |
| 4 | IMMEDIATE, 동시 10건 응답 시간 p95 | 첫 라운드 51.72 ms, 300건 전체 41.96 ms(최대 61.73 ms). 로컬 값 |

- 진 요청의 409 코드는 재고 1개 옵션 하나뿐인 원두에서 전부 `NOT_AVAILABLE`이었다. 첫 주문의 `_sync_sold_out`(4.7.6절)이 원두를 `SOLD_OUT`으로 바꾸므로, 나머지는 조건부 UPDATE에 닿기 전에 판매 상태 확인(4.5.3절 2번)에서 멈춘다. 같은 원두에 재고가 있는 다른 옵션을 하나 더 둔 조건에서는 원두가 `ON_SALE`로 남아 409가 전부 `OUT_OF_STOCK`이었다(IMMEDIATE 270건, 500 0건, p95 54.96 ms. DEFERRED는 `database is locked` 72건).
- DEFERRED의 잠금 오류는 20초 `timeout`을 기다리지 않고 바로 왔다(서버 처리 최대 16.86 ms). 읽기로 시작한 트랜잭션이 그 사이 다른 연결이 커밋한 뒤 쓰기로 올라가지 못하면 SQLite가 대기 없이 `SQLITE_BUSY`를 돌려주기 때문이다. 그래서 `timeout`을 늘려도 DEFERRED의 500은 줄지 않는다.

- 설계에 반영한 사실: `transaction_mode="IMMEDIATE"`(9.1절)는 필수다. 기본값이면 동시 주문에서 500이 난다. 재고는 두 모드 모두 맞았으므로 조건부 UPDATE(`WHERE stock_quantity >= n`, 4.7.6절)와 트랜잭션 롤백이 재고를 지킨다는 설계는 그대로다. 재고 1개 옵션 하나뿐인 원두의 동시 주문에서 진 쪽은 `OUT_OF_STOCK`이 아니라 `NOT_AVAILABLE`을 받는다. 화면 문구(6절)는 두 코드를 모두 "주문할 수 없는 항목"으로 다뤄야 한다.
- 남은 선택: 없음. IMMEDIATE에서 500이 0건이라 11.1절 SQLite 결정의 재검토 신호는 오지 않았다. 운영 서버(t3.micro)에서 같은 스크립트로 다시 잴지는 배포 단계에서 정한다.

### 3.2 toss-confirm-cancel

- 질문: 토스페이먼츠 테스트 키로 (1) 결제창 → `successUrl` 복귀 → 서버 승인, (2) 승인 뒤 전액 취소, (3) 같은 결제를 두 번 취소했을 때의 오류 코드, (4) 결제창에서 연 금액과 다른 금액으로 승인 요청했을 때의 응답이 4.6절 설계대로 오는가?
- 결론: **6단계(10분 만료)만 빼고 확인했다(2026-11-19).** 승인, 전액 취소, 두 번째 취소 거절, 같은 `Idempotency-Key` 재요청은 4.6절 가정대로였다. 다른 금액의 승인 요청은 가정과 달리 토스가 403으로 거절해서, 4.6.3절 3번과 11.1절을 바꿨다. 6단계는 팀장이 건너뛰어 못 잼이다(11.2절 미결).
- 방법: 토스페이먼츠 결제창 SDK 2.10.0(본문 4.6.2와 같은 결제창 방식)과 개발 연동 체험 상점의 테스트 키. 키는 개발용 `.env`(9절)에서 읽고 레포에는 이름만 둔다. `localhost:5173`의 Vite 페이지가 카드 결제창을 열고, 승인·취소·조회는 `spikes/toss-confirm-cancel/toss.py`가 시크릿 키로 부른다. 브라우저는 Chrome 데스크톱. 결제창의 카드사 본인 인증은 팀장이 직접 했다. 결제 두 건(A, B) 모두 1,000원이고, 스파이크가 만든 결제만 승인·취소·조회했다. 코드는 `spikes/toss-confirm-cancel/`, 호출 원본 기록(9건, `paymentKey` 가림)은 `results/calls.jsonl`.
- 결과(시간은 `toss.py`가 잰 요청 왕복 시간):

| 단계 | 확인 | 결과 |
| --- | --- | --- |
| 1 | 테스트 카드 결제 후 `successUrl`에 `paymentKey`, `orderId`, `amount`가 붙어 오는가 | 2건 모두 `success.html?paymentKey=...&orderId=SPIKE-...-P1&amount=1000`으로 왔다. 결제 요청부터 복귀까지 A 36초, B 22초(사람이 인증한 시간 포함) |
| 2 | 승인 응답의 `totalAmount`, `method`, `approvedAt` 값과 형식 | 200, `status: "DONE"`, `totalAmount: 1000`, `method: "간편결제"`(2건 모두. 카드 결제창에서 간편결제 앱으로 인증함), `approvedAt: "2026-11-19T08:51:06+09:00"`(+09:00 오프셋 포함 ISO 8601). A 1,313 ms, B 551 ms |
| 3 | 전액 취소 응답, 같은 결제 두 번째 취소의 오류 코드 | 전액 취소 200, `status: "CANCELED"`, `balanceAmount: 0`, `cancels` 1건(585 ms). 다른 `Idempotency-Key`로 두 번째 취소는 400 `ALREADY_CANCELED_PAYMENT` "이미 취소된 결제 입니다."(215 ms). 조회도 `CANCELED`, `cancels` 1건 |
| 4 | 결제창 금액과 다른 `amount`로 승인 요청한 응답 | 999원으로 승인 요청하면 403 `FORBIDDEN_REQUEST` "허용되지 않은 요청입니다."(211 ms). 결제는 그대로 남아, 이어서 1,000원으로 보낸 승인은 200 `DONE` |
| 5 | 실패·이탈 시 `failUrl`에 붙는 값(창 닫기에 `orderId`가 없는지) | 결제창 X로 닫으면 `failUrl`로 가지 않고 `requestPayment()`가 `{"code": "USER_CANCEL", "message": "취소되었습니다."}`로 실패한다. 2회 모두 같음(Claude 데스크톱 앱 내장 브라우저에서 카드사를 고른 직후 1회, Chrome에서 신한 카드사 창을 닫고 돌아온 뒤 1회). 카드사 창만 닫으면(1회) "인증을 취소하셨습니다." 알림 뒤 토스 결제창으로 돌아오고 페이지 이동은 없다 |
| 6 | 결제 요청 뒤 10분이 지난 `paymentKey`로 승인한 응답 | 못 잼(팀장이 건너뜀). 추정하지 않는다 |
| 7 | 같은 `Idempotency-Key`로 취소를 두 번 보낸 응답 | 1회차 200 `CANCELED`(616 ms), 2회차도 200에 1회차와 같은 본문(`lastTransactionKey`, `canceledAt` 같음, 89 ms). 취소는 1건만 남았다 |

- 5단계에서 창을 닫았을 때는 이동할 페이지가 없으므로 `orderId`가 URL에 붙을 일도 없다. 화면은 `requestPayment()`의 오류를 직접 받아 처리해야 한다. `failUrl`만 보는 설계면 창 닫기를 놓친다.

- 설계에 반영한 사실:
  - 2·3·7단계는 4.6절과 `orders/pg.py` 가정과 같다. 승인은 `status == "DONE"`, 두 번째 취소의 `ALREADY_CANCELED_PAYMENT`는 이미 취소된 것으로 본다(4.6.3절, 4.6.6절). 같은 키 재요청이 오류 없이 첫 결과를 돌려주므로, 4.8.7절의 취소 승인 순서(PG 취소 먼저)는 그대로다.
  - 4단계: 토스가 다른 금액의 승인을 거절하므로 "승인한 뒤 금액을 보고 PG 취소" 경로에는 닿지 않는다. 확인 요청 금액이 결제 시작 때 금액과 다르면 PG를 부르지 않고 결제를 `CANCELLED`로 닫도록 바꿨다(4.6.3절 3번, 11.1절 2026-11-19).
  - 2단계의 `method`는 카드 결제창이어도 `"간편결제"`로 올 수 있다. `EASY_PAY`로 저장한다(4.6.3절 5번 매핑 그대로).
  - 10분 승인 제한(6단계)은 토스페이먼츠 공개 문서 기준 가정으로 남긴다(11.2절).
- 남은 선택: 6단계(10분 만료) 응답. 11.2절에 미결로 둔다.
