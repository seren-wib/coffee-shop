## 8. 확정 사항과 미결

범위, 제품, 진행 방식 결정이다. 요구사항 수준 정책은 SRS 7절, 기술 결정은 SDD 11절에 원문이 있고, 여기에는 계획에 걸리는 것만 요약한다.

### 8.1 확정

- 2026-11-17: 실행 환경을 로컬 PC 시연에서 AWS EC2 배포와 Cloudflare 도메인으로 바꾼다. 버린 것: 로컬 PC 시연(평가자가 직접 접속할 수 없고 배포·운영 요구사항을 다룰 수 없음). 이유: SIP, SMP까지 실제 환경으로 검증한다. (팀장 결정, SRS 7.1절)
- 2026-11-17: 결제는 토스페이먼츠 테스트 모드만 쓴다. 버린 것: 실결제(사업자 등록과 PG 계약 필요). 이유: 비용, 법적 조건. (SRS 7.1절)
- 2026-11-17: 이번 학기 범위 전체를 1차로 두고 차수를 나누지 않는다. 이유: 마감(2026-11-30 23:50)까지 한 번에 배포한다. (SRS 7.1절, 2026-11-19 마감 날짜 정정)
- 2026-11-17: 문서에는 운영 도메인 이름을 적지 않는다. 버린 것: 문서에 이름 적기(공개 레포에 운영 주소가 남음). (팀장 결정, SRS 7.1절)
- 2026-11-17: 단계 문서 원본은 레포 `docs/specs/`이고, Google Docs는 `main` 머지 때 자동으로 덮어쓰는 사본이다. 과제 제출 합본은 따로 만든다. 버린 것: Google Docs에서 직접 편집(이력과 리뷰가 레포에 남지 않음). 이유: 유지보수성. (팀장 결정, CONTRIBUTING)
- 2026-11-17: 배포는 운영자가 서버에서 배포 스크립트를 실행하는 수동 방식이다. 2026-11-19 CI가 들어온 뒤 다시 보고 그대로 둔다. 버린 것: GitHub Actions 자동 배포(SSH 키를 Actions 시크릿에 두고 22번을 열어야 함). 이유: 보안, 종속성. (SDD 11.1절)
- 2026-11-19: 개인정보 수집·이용 동의(FR-58), 처리방침(FR-59), 데모 고지 배너(NFR-36)를 범위에 넣고 이용약관은 두지 않는다. (팀장 결정, SRS 7.1절)
- 2026-09-15: 진행 방식은 GitHub Flow(이슈 → 브랜치 → PR → 스쿼시 머지)이고, 필수 승인 수는 0이다. (CONTRIBUTING, 레포 첫 커밋)
- 2026-11-19: 구현은 TDD로 하고 CI 두 작업(`backend`, `frontend`) 통과를 머지 조건으로 둔다. 이유: 테스트 이름에 요구사항 ID를 달아 SRS부터 PR까지 추적한다. (STP 1절, 7절)
- 2026-11-19: `main` 브랜치 보호를 건다. 필수 검사는 `backend`, `frontend`이고, PR 없이 넣지 못하며 필수 승인 수는 0이다. 관리자에게도 적용하고 force push와 삭제는 막는다. 이유: 승인 0인 대신 자동 검사 통과를 머지 조건으로 지킨다. (레포 관리자 결정, STP 7.2절. 2026-11-19 8.2 미결에서 옮김)
- 2026-11-19: 일정은 마감 2026-11-30 23:50 기준 준비 → 기반 → 기능 병렬 → 통합·배포다(3절). (팀장 전달 마감, #75)

### 8.2 미결

- 시연·평가 기간. 지금 안 정하는 이유: 기간을 알려주는 출처가 없다. 다시 정하는 신호: 일정 공지. (SRS 7.2절)
- 일정이 밀릴 때 무엇을 줄일지. 지금 안 정하는 이유: 아직 밀리지 않았다. 다시 정하는 신호: 기반 단계가 2026-11-23을 넘길 때(3절).
- 조직(5.1절)을 공개 레포에 어떻게 적을지. 지금 안 정하는 이유: 팀장이 정한다. 다시 정하는 신호: 팀장 결정.
